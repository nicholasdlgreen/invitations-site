# Adding a product — the recipe

Written 9 October 2026 so that adding a product stops costing a conversation.
Every rule here is derived from what the 22 live products actually do, not from
preference. **If a rule is written down here, Claude follows it and does not
ask.** The short list of things that still need Nicholas is at the end.

Read `docs/BRAND.md` for voice and `BRAND-IMAGERY-GUIDE.md` for imagery. This
file is the assembly order.

## 2. Field rules — derive, never invent

**Copy the nearest existing product and change only what the rules below say.**
The nearest product is the one with the same shape and the same buying route:
a card you send → `greeting-cards`; an invitation → the nearest occasion's
invitation; an on-the-day piece → its wedding equivalent.

| Field | Rule |
|---|---|
| `slug` | lowercase, hyphenated, the plural noun as a customer would search it |
| `name` | Title Case, plural |
| `supplier_family` / `folded_family` | copy from the nearest product. Never invent |
| `routes` | copy verbatim. This is the flat/folded routing and it is load-bearing |
| `available_sizes` | copy, then **drop any size with no rate** for this family |
| `available_papers` | copy, then **drop any paper with no rate**. Gloss is switched off |
| `available_finishes` | copy |
| `sides_offered`, `envelopes_offered` | copy |
| `quantity_ladder` | **invitations and on-the-day sets: `[10,25,50,100,150,200,250]`. Everyday cards a person sends one of: `[1,5,10,25,50]`** |
| `display_quantity` | the first rung of the ladder |
| `category` | the category of the nearest product. One of `weddings`, `celebrations`, `announcements` |
| `display_order` | the sibling's number; renumber neighbours only if it collides |
| `margin_pct` | **0**, like every other product. Margins are set separately |
| `from_price_text` | leave empty. It is empty on all 23 and nothing reads it |
| `features`, `intro_long`, `buyer_guide`, `faqs` | **leave empty — nothing renders them** |

**Before writing the row, check rate coverage** for every size and paper you are
about to offer:

```sql
select size, paper_name, min(quantity), count(*)
from sheet_rates
where supplier_family = '<family>' and active
group by size, paper_name;
```

A size or paper with no rate must come off the list. Offering one invents a
price — see `docs/STATUS.md` on paper coverage.

## 3. Copy patterns

Derived from the live products. Draft to these shapes, then Nicholas edits.

**Tagline** — 45 to 55 words, four moves in this order:

1. What it does for the customer, in their terms
2. "Printed in the UK on premium/luxurious papers" + a hand-finishing phrase
3. The choice they make — paper and finishing, or what to write
4. "Upload your design or create one with us" (the two routes)

**Description** — one line, about 12 words. Shown on the grid.

**Meta title** — `<Product>, Printed in the UK | foreverprint`

**Meta description** — one sentence, about 20 words, naming the product and the
UK printing.

**Forbidden in all copy** (from `docs/BRAND.md` §6 and the catalogue rule):

- No turnaround or delivery-time promise
- No "proof" — say *check* or *preview*
- **No named finish.** Say "your paper and finishing". Naming a finish risks
  promising something the catalogue cannot supply
- Nothing we do not sell: no wax seals, ribbon, vellum wraps, envelope
  printing, spot UV, deckle edges, cotton rag
- Do not assume a happy reader
- `foreverprint`, lowercase, outside body prose

## 4. Studio wording boxes

Copy the nearest product's `studio_fields` and relabel. Keep `key`,
`preview_style`, `face` and `in_more` exactly as they are — the renderer binds
to them.

**Change only the `label` text**, and **add at most one new box** if the product
genuinely needs a field the sibling lacks. A relabelled clone with no new field
usually means the product should not be separate.

Then run `python3 tools/gen-studio-vocab.py`.

## 5. Imagery

| Spec | Value |
|---|---|
| Path | `/<slug>-hero.jpg` in the repo root |
| Width | **1600px** |
| Aspect | **about 4:3 landscape** (1600×1211 and 1600×1288 are both live) |
| Weight | 170–360 KB |

Follow `BRAND-IMAGERY-GUIDE.md`: overhead flat-lay, soft side daylight, cream or
ivory linen, foliage framing, visible paper texture, never cluttered. Pick a
**florals + prop + background combination no existing product uses** — the guide
carries the differentiation matrix.

**Claude can generate candidates but cannot deliver the file.** Tested
9 October: image generation returns a Canva media reference and a 200x200
thumbnail. `get-assets` returns thumbnails only, `export-design` needs a design
id rather than a media id, and `create-design` would produce something different
rather than wrap the chosen image. There is no route from a generated candidate
to a 1600px JPG in the repo.

**So the hero always ends with Nicholas**, by one of two routes:

1. **Google AI Studio**, the route this guide already specifies — Claude supplies
   the exact prompt, Nicholas generates and downloads at 1600px.
2. **Canva** — candidates Claude generates land in Nicholas's Canva account and
   can be downloaded from there.

Either way the file goes in the repo root as `/<slug>-hero.jpg`, and Claude
crops and resizes it to 1600px at 4:3 with `sips` before wiring it up.

Generated candidates also come out square unless the ratio is forced, and even
then not reliably.

**One caution:** the imagery guide lists wax seals among the gold props and the
Save the Date photograph uses a wax-sealed envelope. We do not sell wax seals.
Do not introduce that prop into new photographs.

## 6. SEO and PPC — what is automatic and what is not

**Automatic, nothing to do:**

- The landing page and order page are generated by the build
- The sitemap entry is generated by the build
- The GA4 and Google Ads tag is on every page via `analytics.js`, so conversion
  tracking and remarketing need no per-product work

**Not automatic:**

- **The mega-menu link — see §7.** Without it the product is reachable only from
  `/products` and search
- **There is no Google Merchant Centre feed.** Shopping ads would be a separate
  project, not part of adding a product

**Watch:** product pages are already about 95% identical to one another. A new
product whose only difference is its name makes that worse. The tagline and the
studio labels are where real difference has to come from.

## 7. The one shared-markup change, and the standing approval

**Product links in `header.html` are hardcoded** — all 22 are literal `href`s in
the mega-menu. A new product needs exactly one line added to the right column.

`header.html` is inlined into every page at build time, so that one line lands
on 53 pages. The house rule is that shared-markup changes need Nicholas.

**Standing approval requested, so this stops being a question:** adding a
product may add **exactly one `<a>` to one mega-menu column and nothing else**.
Claude shows the `header.html` diff in the commit and it must be one line. Any
other change to that file remains a question.

## 8. Verify — in a browser, never by reading

1. `python3 tools/build_pages.py`
2. Load `/<slug>` — hero, tagline and a price appear
3. Load `/<slug>/order` — the quantity ladder shows the expected rungs **for
   every paper**, since unpriceable rungs are silently dropped
4. Configure, add to basket, reach checkout, confirm the quote
5. Check the mega-menu link on desktop **and** at 768px

Then the tests:

```
python3 tools/test-products-grid.py
python3 tools/test-chrome-after-build.py
python3 tools/test-mobile-menu.py
python3 tools/test-one-basket.py
jsc tools/test-occasion-links.js
```

Commit. **Nicholas pushes.** No Publish is needed unless rates changed.

## 9. What still needs Nicholas, every time

Deliberately short:

1. **The copy** — approve or rewrite. Never shipped unapproved
2. **The hero image** — pick from candidates, or supply one
3. **A name that collides with an existing product** — e.g. "New Baby Cards"
   against "New Arrival Cards", whose meta title already claims both phrases
4. **A new size, paper or finish** — never added without asking
5. **The push**

Everything else in this file is decided.
